## 3. Findings that must change the plan (read before building)
**F1 (SECURITY, existing): the browser can mark a user verified today.** `js/verify.js` `submitVerification()` has a fallback: if the RPC `process_verification` "does not exist" it writes `verifications.status='approved'`, `users.is_verified=true` and `taskers.is_verified=true` straight from the browser, and `NAME_MISMATCH` is treated as approved. Even with the RPC present, the page decides success from the RPC result in the browser, and `_publishDrafts()` publishes tasks/services from the browser. That is the exact thing brief phase 6.8 forbids. Whether Postgres RLS already blocks those writes is UNKNOWN until V0 introspect queries 2 to 4 are read. The new work must (a) remove the fallback and the browser-side approval, (b) revoke or trigger-guard browser writes to `users.is_verified/verified_at`, `taskers.is_verified/verified_at/verified`, and `verifications.status`, (c) move draft publishing server-side or gate it on the verified flag.
**F2 (PRIVACY, existing): the old flow stores the raw ID number.** `verifications.id_number` holds NIN/BVN/passport/licence numbers in plain text, plus dob, names, phone. Brief phase 5 forbids unnecessary identity data. The new table stores none of it. Decision D-V2 below: what to do with the existing column and rows.
**F3 (BREAKAGE RISK): `verifications.phone` is read by `db.js` / `js/db.js` (lines about 200, 628, 658) as the contact-phone source** for bookings. Do NOT drop or rewrite that table. Leave it in place and stop writing identity numbers to it; moving the phone is a separate decision.
**F4 (DESIGN): Local Taskers cannot sign in**, so "one general page for both" cannot mean the Local Tasker logs in. The page must run in two modes on the same code and the same tables: `self` (signed-in tasker verifies themselves) and `proxy` (an authenticated coordinator opens it for one of their assigned Local Taskers). In proxy mode the Didit hosted URL is opened on the Local Tasker's own phone (a link the coordinator sends/shows as QR) or on the coordinator's device in the person's presence. Server rule: the Edge Function derives `vendor_data` from the signed-in caller (self) or from a checked coordinator assignment (proxy); it never trusts a user id from the browser.
**F5 (CLAIMS): the mockups promise things we cannot prove.** "NIMC Matched" and "Valid format" shown in the browser, "Bank-Grade Privacy", "NDPR Certified Compliance", "Zero-Liability Verified Guarantee", "Average turnaround 4-6 minutes", "3x booking conversion", "voice consent hash / PKI e-signature", a "QA Simulation Harness" bar, "Verify NIN Direct" button, "Passive 3D Liveness Confirmed" and "99.4% match" shown from the client. None of these is backed by any Didit field or existing table. Build only claims that a stored server result supports; leave the rest out and list them in the report. The QA harness must not ship (brief: no fake or mock results).
**F6 (SCOPE): a hosted flow cannot be styled like the mockups.** Didit's hosted page (`verify.didit.me`) does the document capture, selfie and liveness. StreetTasker's page is therefore the explanation + consent + start + status page. Steps 2 and 3 of the mockup (upload, liveness) happen inside Didit. A custom upload/selfie UI would need the standalone APIs (Approach B), which is not recommended by Didit for end-user flows and would put raw images through our server. Not chosen. Owner to confirm (D-V1).
**F7 (NIN, owner's explicit question): answered.** Document scan does NOT validate against NIMC. NIMC validation is a separate Didit module (`DATABASE_VALIDATION`, Nigeria National ID, listed $0.08 per conclusive call), see `DIDIT-API-FACTS.md`. It must be added to the workflow and its result read from `database_validations[]`. Whether NIN slips / voter cards are accepted OCR documents, and how the NIN is supplied, are UNVERIFIED and need a sandbox test and written confirmation from Didit.
**F8 (CONSENT):** biometric processing (face + liveness) needs recorded consent BEFORE the Didit URL opens (Didit's prompt says the legal layer outside its flow is ours). Self mode: a consent record by the signed-in user. Proxy mode: reuse the existing `local_tasker_consents` pattern (purpose, method in_person/phone/written, `recorded_by` coordinator, evidence ref) with a NEW purpose `identity_verification`; check how purposes are constrained (V0 query 1 and `stage-2b`/`2d` SQL) before inserting.
**F9 (WEBHOOK AUTH):** the webhook Edge Function must be deployed with "Verify JWT" OFF (Didit sends no Supabase JWT), unlike `local-tasker-create`. Its authentication is the HMAC check alone. That is intentional; document it in the deploy steps.

## 4. Proposed design (for the owner to approve before any code)
**Tables (new, additive, RLS on, no browser writes at all):**
- `identity_verifications`: `id uuid pk`, `user_id uuid not null` (StreetTasker user, the `vendor_data`), `tasker_category text check in ('regular','local')`, `provider text default 'didit'`, `provider_session_id text unique`, `workflow_id text`, `environment text check in ('sandbox','live')`, `status text check in (NOT_STARTED, IN_PROGRESS, PENDING, VERIFIED, FAILED, REVIEW_REQUIRED, RESUBMIT_REQUESTED, EXPIRED, ABANDONED)`, `provider_status text` (the exact Didit string), `status_reason_codes text[]` (warning codes only, no personal data), `liveness_ok bool`, `face_match_ok bool`, `document_ok bool`, `nin_database_match text null` (full_match|partial_match|no_match|not_run), `last_event_created_at timestamptz`, `created_by uuid` (self or coordinator), `created_at`, `updated_at`, `completed_at`. Partial unique index: ONE open (non-terminal) row per `user_id` per environment.
- `identity_verification_events`: `event_id text primary key` (Didit `event_id`: the idempotency ledger), `provider_session_id`, `webhook_type`, `provider_status`, `environment`, `received_at`, `processed_at`, `outcome text` (applied | duplicate | stale | ignored_environment | rejected), `payload_hash text`. NO payload body stored.
- Reviews: coordinator "request a re-check" and any manual-review note go to the existing audit log (find its writer in V0 query 6), never to a status column.
**Functions (SQL, service role only, `security definer`):** `idv_apply_event(...)` (single place that changes status; applies the rank/out-of-order rule; sets `users.is_verified`, `taskers.is_verified`, `verified_at`, and for Local Taskers `local_tasker_profiles.verification_method='didit'` and `verified_at`; clears them on `Kyc Expired`; audit row; notification row), `idv_start(...)`, and read functions for the page and the coordinator list (a coordinator sees only their assigned Local Taskers, status + dates + review flag, never scores' underlying images or numbers).
**Status map (Didit string to ours):** none = NOT_STARTED; `Not Started` = NOT_STARTED (session exists); `In Progress`, `Awaiting User` = IN_PROGRESS; `In Review` = REVIEW_REQUIRED; `Approved` = VERIFIED (only after the server re-fetches the decision and every required node is Approved; see D-V3); `Declined` = FAILED; `Resubmitted` = RESUBMIT_REQUESTED (UI text "Action required: redo these steps"); `Abandoned` = ABANDONED (UI: FAILED-style, resume/retry); `Expired` = EXPIRED; `Kyc Expired` = EXPIRED and un-verify. PENDING = the person returned from Didit but the final status has not arrived: set only by the server after reading the session, never by the page.
**Out-of-order rule:** compare Didit `created_at` of the event against `last_event_created_at`; ignore older events; a terminal state (VERIFIED/FAILED/EXPIRED) is only left by `Resubmitted`, `Kyc Expired`, or a NEW session. Always log `outcome`.
**Edge Functions (Deno, in `supabase/functions/`):**
1. `didit-create-session` (Verify JWT ON): input `{ mode: 'self' | 'proxy', local_tasker_user_id? }`. Resolves `vendor_data` server-side, checks consent record exists, calls `POST /v3/session/` (re-used if one is unfinished: Didit does it, we also reuse our row), stores the row, returns ONLY `{url, status}`; never the session token in logs. Retry-safe via a request id like `local-tasker-create`. Maps Didit 403 to "configuration error" for us and "try again later" for the user.
2. `didit-webhook` (Verify JWT OFF): section F9 + `DIDIT-API-FACTS.md` signature steps; checks `environment` matches `DIDIT_ENV`; dedupes on `event_id` (insert-first into the events table); on `Approved` re-fetches `GET /v3/session/{id}/decision/` before applying; returns 2xx within 5 s; 401 for bad signature or stale timestamp; 500 (so Didit retries) if our database write fails.
3. `didit-sync` (Verify JWT ON): the signed-in user (or their coordinator) asks "what is my status": the function reads the Didit session/decision and applies it through the same `idv_apply_event` path. Covers the delayed-webhook case and the return from `callback`. This is the ONLY way the page learns of a result besides reading its own row.
**Frontend:** replace `verify.html`/`js/verify.js` behaviour (keep the file names and route, README lists them). Sections: why, what you need (ID, camera, 5 minutes: do NOT promise "4-6 minutes"), privacy + consent checkbox, "Start verification" (calls `didit-create-session`, then redirects to the returned url; iframe is optional and needs the camera `allow` list), status panel with the six brief messages verbatim, retry/resume, contact support. The status panel reads `identity_verifications` through a read function only. Coordinator: add a status column + filter + "Start or resend verification" to `coordinator-taskers.html`/`js/coordinator-taskers.js`, and replace the "Method / Verified on / Notes" facts in `coordinator-tasker.html` with the real status, completion date and "needs review" flag. No "mark verified" control anywhere. Add `css` only through tokens/existing classes.

## 5. Decisions the owner must make (defaults in brackets)
- **D-V1** Hosted Didit flow (recommended) versus custom UI on standalone APIs. [hosted]
- **D-V2** Old `verifications` rows and `id_number` column: [keep table, stop writing id_number, null out id_number for approved rows after the new flow is live, keep phone]. Needs owner OK because it deletes stored personal data.
- **D-V3** What counts as VERIFIED: [Didit overall `Approved` AND liveness Approved AND face match Approved AND (when a Nigerian document is used) NIMC database validation `full_match`; anything else is REVIEW_REQUIRED or FAILED]. Partial NIN match = review.
- **D-V4** Do customers also use this flow? Current page serves both roles; the brief names taskers only. [taskers only first; customers keep a blocked-not-approved state until decided; the unsafe browser fallback is removed for everyone]
- **D-V5** Who reviews `In Review`? [Didit console reviewers = the owner/admin; no StreetTasker manual-approve UI; coordinators only see "needs review"]. If a StreetTasker review UI is wanted, it belongs to Stage 8B (admin).
- **D-V6** O3 (verification record location): [`identity_verifications` is the record; `local_tasker_profiles.verification_method/verified_at` are written only by `idv_apply_event`]. And whether VERIFIED becomes a blocking publish check (currently a recommendation).
- **D-V7** Retention: Didit keeps session data per its own retention settings; set them in the console and decide whether to call the delete endpoint on account closure. [owner decides after reading Didit's retention page]
- **D-V8** Legal: privacy policy / NDPA wording for biometrics (the site has `privacy.html`). Not drafted by this package; the claims in F5 stay out until a lawyer approves wording.

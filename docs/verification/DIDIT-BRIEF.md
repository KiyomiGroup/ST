# StreetTasker x Didit: owner's brief (verbatim summary of the 9 phases)

Source: owner message of 2026-10-30. Official doc: https://docs.didit.me/integration/integration-prompt
This is an integration into the EXISTING site. Do not rebuild it or touch unrelated features.

PHASE 1 Inspect first (stack, auth, roles, normal/local/coordinator representation, existing verify page, Supabase tables/policies/Edge Functions/buckets, coordinator screens). Give a short assessment BEFORE changing code. Do not assume the stack.
PHASE 2 Didit integration: ID document verification, authenticity, selfie, face match, liveness, decision retrieval, session creation, signed webhooks, error handling and retries. Never invent endpoints, events or SDK methods. CONFIRM whether Nigerian NIN database validation is separate from document verification. Do not assume scanning a document validates the NIN against NIMC.
PHASE 3 ONE general verification page for normal AND local taskers (one infrastructure). Explain why, what is needed, privacy notice + consent, start Didit, show status, resume/retry, failure instructions, desktop + mobile, existing green brand.
PHASE 4 Coordinator dashboard: see a local tasker's status; who has not started; pending/completed; initiate or resend an invitation; send them to the general page; completion date; whether review is needed. Coordinators can NEVER mark someone verified by a button. Only an authenticated, validated Didit result authorises VERIFIED. Manual review (if any) needs an audit trail.
PHASE 5 Database: statuses NOT_STARTED, IN_PROGRESS, PENDING, VERIFIED, FAILED, REVIEW_REQUIRED, EXPIRED (adapt to Didit's real statuses). Each record: StreetTasker user id, tasker category, Didit session id, status, created/updated/completed timestamps. No duplicate records, no duplicate webhook processing. RLS. Do not store documents, raw biometrics or unnecessary personal data. Do not destroy existing data.
PHASE 6 Webhooks: verify signature per Didit, reject invalid, idempotent, no duplicate updates, correct user+session, handle delayed/failed/out-of-order, log without sensitive data, frontend cannot change status. Secrets server-side only, exact Didit credential names.
PHASE 7 User messages: Not Started "Your identity verification has not been completed." / In Progress "Your identity verification is currently underway." / Pending "We are waiting for the verification result." / Verified "Your identity has been successfully verified." / Review Required "Your verification requires additional attention." / Failed "Your verification could not be completed. Follow the instructions to try again or contact support." Notifications on change. Never show success before the backend validated the result.
PHASE 8 Test: success, failure, face mismatch, failed liveness, incomplete session, pending, delayed webhook, duplicate webhook, invalid signature, Didit API down, user reading another user's record, coordinator initiating for a local tasker, normal + local registration flows, desktop + mobile. Use Didit sandbox. No real people's documents.
PHASE 9 Deployment prep for the EXISTING hosting. Provide env vars, migrations, webhook endpoint config, Didit dashboard steps, deploy, sandbox test, production activation steps. Do NOT deploy or activate live verification without the owner's approval.

RULES: no redesign of unrelated pages; remove nothing; no second auth system or user database; no hardcoded credentials; no faked or mocked results in production; never mark verified from the frontend; confirm every Didit feature in its docs; keep the design system.

FINAL REPORT must list: what was built; files modified; files created; DB changes/migrations; env vars; Didit dashboard steps; webhook config; tests run and results; outstanding issues; exactly what the owner must do to go live. If a credential, dashboard setting or provider feature is missing, say so instead of pretending.

## 1. What this stage did
- NEW SQL `sql/local-tasker/stage-4c1-core.sql` (re-runnable, additive, changes no existing object):
  - `_local_tasker_readiness(uuid)` (internal, service_role only): the publish checklist as JSON `{ready, checks[{key, ok, blocking}], services, photos}`. BLOCKING checks: `not_retired` (status is draft/ready/published), `public_name` (users.name 2+ chars), `tasker_row` (a `taskers` row exists), `agreement_profile`, `agreement_publish` (active consents), `agreement_photos` (only when photos exist), `service` (at least one active service with price > 0), `private_clear` (no phone/whatsapp on `taskers`, no whatsapp/dob on `users`: publishing makes those rows public). RECOMMENDED only: `verification` (method and date recorded), `photo` (at least one).
  - `local_tasker_publish_status(p_tasker)` (rpc, authenticated): the managing coordinator reads the checklist plus `status`.
  - `_local_tasker_sync_public(uuid)` (internal): copies the PRIMARY service (oldest active service with a price) onto the `taskers` row like `postService` does: service, service_name, category, rate_value, price, rate_unit, `rate` text such as `₦12,500/job`, location (service location, else areas served), bio, description, specialties, availability_status, `available = true`; `is_verified`/`verified` false; `photo_url` and `photo` left EMPTY (see D46).
  - `publish_local_tasker(p_tasker)` (rpc): authority from `auth.uid()` (active coordinator who currently manages the person, else hint `not_found`); locks the profile row; refuses with hint `not_ready` (message lists the failed keys) unless every blocking check passes; syncs the `taskers` row; sets `status = 'published'`, `published_at`, `published_by` the first time; audit `local_tasker_published` (no phone, no full name). Pressing it on someone already published only refreshes the `taskers` row and logs `local_tasker_listing_refreshed`. Returns `{status, already_published, primary_service_id}`.
  - `unpublish_local_tasker(p_tasker, p_reason)` (rpc): same authority; reason up to 300 chars (`bad_input`); sets profile `status = 'ready'` and `taskers.available = false`; nothing deleted; audit `local_tasker_unpublished` with the reason; not published => `{changed:false}`.
  - Customer-safe, callable by `anon`: `local_tasker_public_info(p_ids text[])` returns `(user_id, cover_path)` ONLY for PUBLISHED Local Taskers among up to 100 ids; `local_tasker_public_photos(p_tasker)` returns `(path, caption, is_cover)` of a published person, max 8.
  - `local_tasker_photo_is_public(name)` plus ONE storage policy `lt_photos_storage_public_read` (select, anon and authenticated, bucket `local-tasker-photos` only): a file can be read (through signed links) only while its owner is published and the photo is not removed. The bucket stays private.
- NEW `stage-4c1-rollback.sql` (drops the functions and the policy; data stays; people already published stay published) and `stage-4c1-tests.sql` (self-rolling-back, NOT RUN).
- NEW page `coordinator-publish.html` + `js/coordinator-publish.js` (`?id=<tasker uuid>`): checklist with fix links (service form, photos), the Customer view preview (public name only, both labels together, area, primary service, rate, description, specialties, up to 3 photos through signed links, the inclusive-economy note as plain text), Publish (needs a ticked confirmation that the person agreed), Update public listing, and a two-step Unpublish with optional reason. Every failure shows `Error code: <code>`.
- Profile page: a "Publishing" card (status sentence and a Preview and publish / Manage listing button; hidden for retired profiles). Nav highlight and `.co-pub-*` CSS (tokens only).

## 6. Decisions the next AI must know
- D46: Customers see Local Tasker photos ONLY through short-lived signed links (`createSignedUrls` on the private bucket), allowed by `lt_photos_storage_public_read` while the person is published and the photo is not removed. `taskers.photo_url` and `services.photo` stay EMPTY for Local Taskers. Customer pages must ask `local_tasker_public_info(ids)` for the cover path and sign it in the browser. A link already issued keeps working until it expires (about an hour) after an unpublish.
- D47: Only `publish_local_tasker` / `unpublish_local_tasker` change `status` to or from `published`. Unpublish goes to `ready` (hidden), keeps `published_at`. A `inactive` (retired) profile can never be published.
- D48: `verification` and `photo` are recommendations, not blockers: no function records verification yet (O3 default is a coordinator record in the profile row) and a photo is optional.
- D49: Publishing copies the primary service onto `taskers`. `save_local_tasker_service` does NOT re-sync (4B-1 is untouched), so after changing a published person's service the coordinator presses "Update public listing". The marketplace reads `services` directly, so prices there are current at once; only the `taskers` mirror needs the refresh.
- D50: The Local Tasker badge on customer pages comes from `local_tasker_public_info`, never from a column on `users`/`taskers`/`services` (D2). "Hide Make offer / Apply" needs NO UI work: a Local Tasker has no login (banned placeholder identity), so no such page can ever be shown to one; enforcement is the existing `local_tasker_block_applications` trigger, tested in `stage-4c1-tests.sql`.

## 9. Security and backward-compatibility
Authority is decided in the database from `auth.uid()`. Nothing from the browser decides status. Customer-safe functions return only published people and never a name, phone, notes or status. Private contact data on the public rows blocks publishing. Photo files are readable only while published and not removed; the bucket is still private; no update or delete policy exists. No existing policy, function or table changed: regular taskers and customers behave exactly as before. Audit rows hold ids, counts and the unpublish reason only.

## 10. Known limitations and DANGER between 4C-1 and 4C-2
- IMPORTANT: until 4C-2 is built, a published Local Tasker appears in the existing marketplace like any other tasker: NO "Local Tasker / Phone Assisted" label and NO picture (customer pages do not know about signed links yet). A customer can also still insert a booking for that person (stage 2C observation; blocked later in 5A). So publish a test person only to try the screen, then UNPUBLISH at once, and do not publish a real person before 4C-2 and 5A.
- No automatic refresh of the `taskers` mirror (D49). Verification cannot be recorded anywhere yet. No admin override. The checklist is not re-checked after publishing except when the coordinator opens the page or presses a button.
- On a phone, the preview sits below the Publish box (one-column order).
- Anonymous reads: the 2C observation says `anon` has no SELECT grant on `users`/`taskers`; if `find-taskers` embeds `users` for visitors that is an existing behaviour 4C-2 must check, not something 4C-1 changed.

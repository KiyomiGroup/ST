## 1. What this stage did
- NEW SQL `sql/local-tasker/stage-4b1-core.sql`: function `public.save_local_tasker_service(p_tasker, p_service_id, p_name, p_category, p_price, p_rate_unit, p_description, p_location, p_specialties, p_availability, p_available, p_consent_method, p_consent_evidence, p_consent_details) returns jsonb` (`{service_id, created, changed[]}`). SECURITY DEFINER, `search_path = public, pg_temp`, granted to `authenticated` and `service_role` (NOT `anon`). Same authority pattern as 4A-3 (D34): caller = `auth.uid()`, must be an active coordinator who currently manages the Local Tasker, else hint `not_found`.
- It writes ONLY `public.services` rows whose `user_id` is that Local Tasker: create, or change one of THEIR services (another user's service id gives `not_found`). Never deletes: a service is paused with `available = false`. `verified = false`, `rating = 0`, `reviews_count = 0` always. Max 5 services each (`service_limit`). A second service with the same name (case-insensitive) is refused on create (`duplicate_name`).
- Validation (hint `bad_input`): title 3-100; category `^[a-z][a-z_]{1,39}$` (so existing categories such as `laundry_services` still work); price greater than 0 and at most 10,000,000 (rounded to 2 places); unit one of `/hour /day /job /visit /session` (the units the site already uses); description 10-1000; location up to 200 (empty = the Local Tasker's `areas_served`); up to 10 specialties of 1-40; availability one of `available_now / available_today / available_this_week`.
- AGREEMENT: if the Local Tasker has no active (not withdrawn) `publish_info` consent, the first save REQUIRES `p_consent_method` (`in_person|phone|written`; else hint `consent_required`, nothing written) and records the consent row (+ audit `consent_recorded`) in the same transaction. Once one is on record, later saves send no agreement.
- AUDIT: `local_tasker_service_created` and `local_tasker_service_updated` (entity `local_tasker_service`). Updated rows keep the changed field NAMES and the price/unit/available before and after (public facts, not private). A save with no change writes nothing.
- NOT done by this function (on purpose): publishing; syncing the `taskers` row (service, category, rate, location, bio, photo, available) that the existing `postService` keeps in step; any customer visibility. The existing RESTRICTIVE policy `lt_hide_unpublished_services` hides these services from everyone except the managing coordinator and admins until the profile is `published`. The `taskers` sync belongs to 4C (publish).
- NEW `stage-4b1-rollback.sql` (drops the function; saved services, consents and audit stay) and `stage-4b1-tests.sql`. `stage-4b-inputs.sql` is the read-only query the owner ran for storage facts.
- NEW page `coordinator-service-edit.html` + `js/coordinator-service-edit.js`: `?id=<tasker uuid>` (add) or `&service=<service uuid>` (edit). Hero/card style of the other coordinator pages. Reads the profile, the service (filtered by both ids, under RLS) and whether a `publish_info` consent exists; shows the agreement fields only when none exists. Saves through `window.supabase.rpc('save_local_tasker_service', ...)` with only the function's arguments. Price accepts `12500`, `₦12,500`, `12,500.50`. Errors are shown with `Error code: <code>` (`not_found`, `bad_input` with the server message, `service_limit`, `duplicate_name`, `consent_required`, `unauthenticated (42501)`, `server_error (<code>)`, `network`, `bad_response`). A lost response on create tells the coordinator to check the profile before saving again (there is no request id; the duplicate-name guard is the safety net). Redirects to `coordinator-tasker.html?id=...&service_saved=created|updated|none`.
- Profile page: a "Services and agreed rates" card (name, category, price per unit, Active/Paused, description, Edit service; Add service button, hidden at 5). It loads separately so a problem there never hides the profile. Banners for the three outcomes.

## 3. Decisions and things the next AI must know
- D37: Services are saved through an RPC with in-function authority (same as D34). No Edge Function.
- D38: Consent purpose written by 4B-1 is `publish_info` (agreement to have service information published and to the agreed rate), required once. `price_change` is reserved for later price changes on bookings (5C). `photos` consent is for 4B-2.
- D39: A service is paused, never deleted (no destructive actions); 5 services maximum per Local Tasker; the services of a Local Tasker are never `verified` and have no rating.
- D40: The `taskers` row is NOT synced in 4B-1. At publish (4C) a SECURITY DEFINER function must set the `taskers` fields from the primary service the way `postService` in `js/db.js` does (service, category, rate_value, rate text like "₦12,500/job", location, bio, photo_url, available) and flip the profile to `published`. Until then `taskers.available` stays false.
- Existing policies on `services` (from the owner's export): permissive `Public can read services` (anon, true), `auth_read_services` (true), `services: public read available`, owner policies by `user_id = auth.uid()`, and the RESTRICTIVE `lt_hide_unpublished_services`. A Local Tasker can never sign in, so the owner policies never apply to them.

Sections: A functions (anon or PUBLIC can run an admin function, definer without fixed search_path, helpers open to users), B tables (RLS off, anon and browser write rights, money tables writable, views that bypass RLS), C policies and private columns (`users`/`taskers` readable by everyone), D secrets (trigger, cron job and function text that contains a token; **names only, the value is never returned**), E admin accounts (count, two Super Admins, MFA, stale logins, `support_staff` strays), F sensitive columns, card rows, `topup`, G storage buckets, H audit-log immutability. It returns no email, phone, ID, account number, address, authorization code or any row of personal data (admin ids are cut to 8 characters).

7. **Static audit of the repo (done, no database needed).** Read all 146 functions in `sql/admin/*.sql` (rollback and test files excluded):
   - **OK.** Every `admin_*` function the browser can call is SECURITY DEFINER with a fixed `search_path`, checks a permission (directly, or through `admin_guard`, the approvals scope check, or `_admin_dispute_run`), and is revoked from `public` and `anon` before `grant execute ... to authenticated`. A9, A10, A12a and A12b do this with a loop over the function names. The internal helpers (`_a10_pick`, `_a15_*`, `_a16_*`, `_a18_*`, `_acct_*`, `admin_has` and the guards) are revoked from the browser. The only non-definer `admin_*` functions are trigger and helper functions (`admin_approval_guard`, `admin_approval_hash`, `admin_audit_immutable`, `admin_feed_expr`).
   - **OK.** `admin_audit_log` has update/delete and truncate blocking triggers (A1). `/admin` has `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `no-store`, `noindex`, `no-referrer`, `nosniff` in `vercel.json`, `Disallow: /admin/` in `robots.txt`, `noindex` in every admin page and in `support.html`.
   - **OK.** Admin JavaScript writes text with `textContent` only (one `innerHTML` mention, in a comment saying it is never used); no `eval`, `document.write`, `new Function`; no role read from `user_metadata` or `app_metadata`.
   - **FINDING S-1 (medium). Supabase client loaded from a CDN, unpinned and without integrity check.** All admin pages load `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2/dist/umd/supabase.min.js`. `@2` floats to any new 2.x release and there is no `integrity=` attribute, so a compromised or mistaken release would run inside an admin's signed-in session. Fix (small, needs a go): pin an exact version and add an SRI hash, or save the file in the repo and serve it from `/admin/vendor/`. The same pattern is probably on the public pages (not checked in this stage).
   - **FINDING S-2 (low to medium). `/admin` has no script restriction.** The header sets only `frame-ancestors`. A real Content-Security-Policy (`default-src 'self'`, `script-src 'self'` plus the one pinned CDN or none if self-hosted, `connect-src 'self'` plus the Supabase project URL, `img-src 'self' data:` plus storage) would limit damage from S-1 and from any future mistake. Pages have inline `<script>` blocks today, so a CSP needs a short test pass first; not done here.
   - **FINDING S-3 (low). `admin-disputes.js` reads four tables directly** (`dispute_events`, `job_refunds`, `job_attachments`, `job_disputes`) and makes signed links for `job-evidence`. The spec says admin pages use `admin_*` functions only. The reads work because of the older staff policies (`_is_support()`), so they are **not** checked against the admin permission `disputes.view`: anyone in `support_staff` gets them, whatever their admin role. Fix: add reader functions (a small A13 follow-up) and drop the direct reads. Not changed here.
   - **Not checkable from the repo:** the live grants, policies, triggers, cron commands and storage, the 8 Edge Functions that are not in the repo, and whether `ARCHITECTURE.md` Part C items 6 to 12 are still true today. That is what the query in item 5 answers.

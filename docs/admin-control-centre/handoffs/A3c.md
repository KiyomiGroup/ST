8. **Decisions made.** (a) **Set-up is only on My profile, never on the sign-in page.** If it were offered at sign-in, anyone with an admin's password could enrol their own phone and pass two-step. Cost: an admin added while `require_mfa` is on cannot enrol; the Super Admin switches it off with `a3c-mfa-off.sql`, the new admin enrols, then it is switched on again (a later team-management stage can improve this). (b) `a3c-mfa-on.sql` refuses to switch on unless **every active admin** has a verified authenticator, and prints who is missing: this is the lock-out guard. (c) The last authenticator cannot be removed on the page while two-step is required. (d) Removing a factor at `aal1` may be refused by Supabase (needs `aal2`); the page then says to sign in again with the code. (e) Help is static text; the escalation contact is "the owner (the Super Admin)" because no escalation address was ever given. (f) Help does not link to the handoff docs (see item 12).
9. **Tests.** Item 2. Design check: no admin file in its failure list; it still fails on older files (`css/legal.css` and others), as before A3a.
10. **Security notes.** The QR picture is only drawn if it is an SVG data image from Supabase; the set-up key is shown once and not stored. A password plus a stolen, already-enrolled phone is out of scope. Recovery if a phone is lost: run `a3c-mfa-off.sql`, then remove that login's factor in the Supabase dashboard (Authentication, Users, the user, MFA) and enrol again.

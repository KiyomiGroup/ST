# Stage A5e: invite a new admin (2026-11-09)
1. **Objective.** Let a Super Admin invite a new person as an admin, only after a different Super Admin approves, creating the login with the service-role key kept on the server. Last of five parts of A5 (S08).
2. **Done.** Written, and tested only against fakes: `sql/admin/a5e-invite.sql` (+ `a5e-rollback.sql`), Edge Function `supabase/functions/admin-invite/index.ts` (+ one-file copy in `supabase/deploy/admin-invite/index.ts`), `admin/accept-invite.html` + `admin/js/admin-accept-invite.js`, and an Invite panel on `admin/team.html` (`admin-team.js`). **The SQL was NOT run anywhere (no Postgres in this build environment). The function was NOT run in Deno or against real Auth (no Deno, no network).** Nothing run on Supabase; nothing deployed.
3. **Files inspected.** `a2-approvals.sql` (request, consume, registry), `a5d-team-write.sql` (pattern), `a1-admin-core.sql` (tables, bootstrap lookup), `supabase/functions/local-tasker-create/index.ts` (CORS, token check, service-role pattern), `supabase/deploy/build-bundles.mjs`, `admin-login.js`, `admin-team.js`, `admin-change.js`, `admin-profile.js` (password rule), `js/supabaseClient.js`.

5. **Files modified.** `admin/js/admin-team.js` (invite panel; header comment), `admin/team.html` (one sentence of intro text only), docs. `build-bundles.mjs` was **not** changed on purpose: its `strip()` deletes every line starting with `import`, which would remove the Supabase import. The deploy copy is the source file plus one comment line.
6. **Database changes.** Run once, whole file `a5e-invite.sql`; last line must say `DONE: A5e installed`. Needs A1, A2, A5d. Adds ONE row to `admin_sensitive_actions` (`admin.team.invite`, permission `admin.team.manage`, high risk, 72 h) and functions only. Rollback `a5e-rollback.sql`.
7. **RLS and grants.** No table or policy touched. `authenticated` may execute `admin_invite_request`, `admin_invite_precheck`, `admin_invite_finish`, `admin_invites_mine` (each checks its own permission). `admin_invite_auth_lookup` is `service_role` only; `admin_invite_target_version` has no browser access.
8. **Functions.** SQL: as above. Edge: `admin-invite` (POST `{approval_id}`, Verify JWT ON). It calls `precheck` as the caller, creates the login (`auth.admin.inviteUserByEmail`), then calls `finish` as the caller. The caller's token is used for both database calls so the A2 consume rule "only the requester runs it" is enforced by the database, not the function.
9. **Rules enforced.** Needs `admin.team.manage`; approver is a different Super Admin; the requester sends; the approval is used once, in the same transaction as the `admin_users`, role and (Super Admin only) `support_staff` rows; at least one existing role; the email must be new for admin work (refused if already an admin, or if it already has a `public.users` or `coordinators` row); email and roles come from the approved row, never from the browser; the login created must match the approved email; every ask, refusal and invite is in `admin_audit_log` (`admin.team.invited`, refusals as `admin.invite.finish`).
10. **Decisions made.** (a) Own registry action `admin.team.invite` instead of reusing `admin.team.change`, so the A5d panel and reader do not need to understand it. (b) **A separate login is required** (stricter than the A1 bootstrap, which let the owner reuse a coordinator login): easy to relax in `admin_invite_request` and `admin_invite_finish` if you disagree. (c) The admin row is made when the invite is sent, so it is active before the person chooses a password; they cannot sign in until they do. (d) A new page `accept-invite.html` sets the password; no other page does that. (e) If a bare login with that email already exists (no site account), it is reused and no email is sent; the toast says so. (f) No resend button (see 14).

A5d (43) and A5c (41) still pass. Function logic (Node, fake clients): `a5e-function-test.mjs` **19 checks pass** (order of steps, caller token used for both database calls, body email and roles ignored, foreign origin, 401, 400, 405, missing secrets, precheck refusal creates no login, site-account refusal, reused login, email failure leaves the approval unused and leaks nothing, finish failure message). **Not run:** the SQL anywhere, Deno, real Supabase Auth, a real invite email, two real admins, mobile Safari.
12. **Security notes.** The service-role key exists only inside the function. The invite goes to the email on the approval: **the approver should read it on Pending approvals before approving** (the page shows the payload). Whoever opens the email link can set the password, so a wrong address hands admin access to that person: check it. The link is short lived. `require_mfa` is still off by default, so turn it on (A3c) once the new admin has set up an authenticator app. `accept-invite.html` grants nothing: it asks the database whether the login is an active admin and signs out anyone who is not.
13. **Backward compatibility.** No existing table, policy, trigger or function changed; no site page, `support.html`, `js/auth.js` or coordinator page touched. Existing A5d requests and pages unchanged (their tests pass).
14. **Outstanding issues and known limits.** (a) **SQL untested: if the first run errors, paste the message** (nothing changes on error). (b) **No resend**: if the link expires or the email never arrives, there is no button to send it again, and I have not verified a safe dashboard workaround, so ask me for a small resend action rather than improvising. (c) Supabase's built-in email sender has a low hourly limit; configure custom SMTP if you invite several people. (d) If a database trigger on `auth.users` creates a `public.users` row for every new login (none is in the repo; the Supabase dashboard might have one), the finish step refuses with "has a customer, Tasker or coordinator account" and no admin is made; tell me and I will adjust. (e) An admin who later visits a customer page may get a `public.users` row from the site's sign-in code (`js/auth.js`); that is the open item about `admin@streettasker.com` being also a customer row (separate small stage).

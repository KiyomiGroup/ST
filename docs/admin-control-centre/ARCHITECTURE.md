### A1. Stack
- 74 HTML pages at the repo root, 130 JS files in `js/`, 56 CSS files in `css/`, shared markup in `components/` (`navbar.html`, `footer.html`, `bottom-nav.html`, `coordinator-nav.html`). - Service worker `sw.js` (v4): serves only `offline.html` when a page cannot load; it never stores pages, API calls or sign-in. Admin pages are therefore never cached by it. - `robots.txt` starts with `Allow: /` and then lists Disallow lines per page. `support.html` relies only on a `noindex` meta tag. Admin pages need both the meta tag and `Disallow: /admin/`.

### B5. Answers to the questions the plan asked (D-A14, D-A16 and the A0 list)
1. **Where the platform fee is stored.** Per payment row, as an amount: `escrow_payments.platform_fee`, `payment_intents.platform_fee`, `payments.platform_fee` (each next to `tasker_amount`). For Local bookings: `local_booking_commissions` (`base_amount, fee_total, coordinator_share, platform_share, status credited|adjusted`). The **rate** comes from the function `platform_fee_rate()`, whose source was not shown, so where the 12 percent (and the later 2 percent transport and materials rule) lives is **unknown**; `platform_fee_rate_for_booking` ignores the booking, so today it is one global rate. `local_booking_quotes.service_fee` is the quoted service charge, **not** the platform fee. Withdrawal fee: `withdrawals.fee` and function `withdrawal_fee(amount)`. Revenue reports (A16) must therefore sum stored fee amounts, never recompute from a rate.
2. **Which table holds Local booking state.** `local_booking_state` (see B4).
3. **Real coordinator tier table.** There is **no tier definition table**. `coordinator_tiers_state(coordinator_id, tier)` holds each coordinator's tier; `coordinator_tier_upgrades` is the purchase ledger (from_tier, to_tier, amount_kobo, payment_reference; UPDATE blocked by trigger); `coordinator_tier_terms(p_tier)` is an INVARIANT function returning `capacity` and `price_kobo` (tiers 1 to 100), and `coordinator_capacity(p_coordinator)` returns the cap. Values per tier are unknown (source not shown).
4. **Does the 10-worker limit exist?** **Not as a fixed 10.** It was replaced (Stage 7G) by a per-tier capacity enforced in the BEFORE INSERT trigger `coordinator_assignments_guard` (function `local_tasker_assignment_guard`): it locks the coordinator row, refuses a coordinator who is not `active`, counts assignments with `ended_at is null`, and refuses when the count reaches `coordinator_capacity()`. Assignments cannot be edited or deleted (only `ended_*` can be set once). `local_tasker_max_active()` still exists (legacy, probably reading `local_tasker_settings`). **Consequence: A9 does not build the limit; it must reuse this trigger and never bypass it.** What tier 1 allows is unknown until F3 runs.
5. **`support_staff` and `is_local_tasker_admin`.** See B1 and B2.
6. **Are coordinator codes still used?** **Yes, internally.** A person who passes the coordinator test gets a code (`coordinator_applications.code`, approved by `admin_approve_coordinator_application`); `coordinator-signup.html` calls `coordinator_code_check(p_code)` and the database spends the code in `coordinator_finish_signup()`. `coordinator_codes` (code, expires_at, application_id, used_by, used_at) is the store. `admin_create_coordinator_code(note, days)` is the manual route. Whether D-2's SQL (switching off `coordinator_redeem_code`) was run is unknown. Decision for A9: **no separate Codes screen**; the Coordinators page shows each application's code state, with a small "Create a code" action only if the owner still wants manual codes.
7. **Allowed status values.** `services.listing_status`: `active`, `paused`. `job_disputes.status`: `open`, `under_review`, `resolved`, `withdrawn`. `bookings.status`: no constraint; **the real values in use (owner's a10-check result, 2026-11-09) are `pending` (5), `confirmed` (4), `completed` (11), `cancelled` (3)**; others may exist later and are shown as stored. `tasks.status`: `open, in_progress, completed, cancelled, draft`. `task_applications.status`: `pending, accepted, rejected, closed, withdrawn, cancelled`. `payment_requests.status`: `pending, processing, paid, failed, declined, cancelled, refunded`; kinds `payment, full_payment, remaining_payment, transport, materials, additional_cost, invoice, refund`. `payment_intents.status`: `pending, paid, expired, failed, amount_mismatch`; purposes `request, booking, topup, tier_upgrade, subscription`. `withdrawals.status`: `pending, processing, success, failed, reversed`. `local_payouts.status`: `queued, processing, paid, failed, review, reversed`. `gift_cards.status`: `active, redeemed, void`; `gift_card_orders.status`: `pending, paid, failed, refunded`. `verifications.status`: `pending, approved, rejected`. `local_tasker_profiles.status`: `draft, ready, published, inactive`. `messages.request_status` has 12 values. `local_booking_commissions.status`: `credited, adjusted`.

## Part C: risks found so far (for the owner; none are fixed by this stage)
1. Role read from `user_metadata` (A3 above). Admin must not reuse it.
2. Urgent-task fee (`URG-` reference, `js/tasks.js` line ~502) is confirmed only in the browser (the owner's issue X1).
3. Eight Edge Functions on the money and notification paths are not in the repo, so their behaviour cannot be audited from the code.
4. No security headers in `vercel.json`; `robots.txt` does not list `support.html`.
5. Repo copies of some functions are stale; deployed copies rule.
6. **CRITICAL: secrets appeared in the owner's pasted results (found in A0 part B).** (a) The trigger `push-notifications` on `notifications` has the full request headers written into its definition, including an `Authorization: Bearer` token that decodes as a **`service_role` key** for this project (role claim `service_role`, expiry in 2036) and an `x-push-secret`. (b) The cron job `gift-card-deliveries` has an `x-cron-secret` header in its command. A service-role key bypasses all row level security. These values are now in this chat and in the uploaded CSV files. They are **not** repeated in any file of this pack and must never be copied into one. Recommended: treat all three as exposed and rotate them, and move the push trigger and the cron call to read secrets from Supabase Vault instead of literal text. This is a separate security stage (**S1** in `00-PLAN.md`), not part of the admin build, and the owner decides when. Do not run it without the owner, because rotating the service-role key breaks every Edge Function until its environment value is updated.
7. **Browser roles hold far more table privileges than needed.** `anon` has table-level SELECT on `wallets`, `wallet_transactions`, `payments`, `escrow_payments`, `payment_intents`, `payment_requests`, `messages`, `message_threads`, `bookings`, `verifications`, `notifications`, `tasks`, `services` and 14 more tables (25 in all). Row level security (ON for all 121 tables) is what blocks the reads, so this is defence in depth, not an open door; but one missing policy would expose a table. `anon` and `authenticated` also hold ALL privileges, including TRUNCATE, on `notification_preferences`, `push_subscriptions` and `user_tour_progress`. TRUNCATE ignores row level security, but the browser API cannot send TRUNCATE, so this is not reachable from the website. Both belong in A27.
8. **Every logged-in user can read every row of `users` and `taskers`** (policies `auth_read_users`, `auth_read_taskers`, `taskers: read` are `true`). Columns on `users` include `dob`, `whatsapp`, `contact_violations`, `is_flagged`, `flagged_reason`. Column-level privileges were not checked. For admin this means the flag columns are not private today. A27 decides whether to narrow this; do not change it inside an admin stage.
9. **`payment_intents.purpose` still allows `topup`** (CHECK constraint) while rule R-W says the site takes no top-ups. No `topup` rows exist, so nothing is broken. It is the T1 item already in `SUBSCRIPTION-HANDOFF.md`.

11. **Sensitive columns sit in clear text:** `verifications.id_number`, `withdrawal_bank_accounts.account_number`, `withdrawals.account_number`, `booking_private.address`. Admin shows only masked values with a logged Reveal (D-A12) and never exposes `id_number`.
